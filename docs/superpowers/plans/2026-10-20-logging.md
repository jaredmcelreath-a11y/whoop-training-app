# Logging (Plan 2) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A **Log** tab where the owner records everything WHOOP can't see:
- strength sets (with "last time" numbers), runs, gym-bike rides and pool swims;
- daily weight, plus a one-tap weight tile on Today;
- 0–10 pain ratings by body area;
- weekly VO2 max and WHOOP Age;
- body scans and lab panels.

The owner's existing baseline is loaded from a private file.

**Architecture:**
- Each kind of entry gets its own table and a small `src/lib/log/*` module of pure server functions taking `db`. Each function is unit-tested against PGlite.
- Pages under `src/app/log/` use server actions. Every action calls `requireSession()` itself and validates input with zod before writing.
- A shared `TabBar` component replaces Today's inline tab bar.
- Entries are matched to overlapping WHOOP workouts, so heart rate and strain show next to the manual numbers.

**Tech Stack:** As in Plan 1: Next.js 16 (App Router, `cacheComponents`), TypeScript, Drizzle (PGlite dev/test, Neon prod), zod, Vitest, CSS modules.

**Spec:** `docs/superpowers/specs/2026-10-20-training-app-design.md`, sections 6 (manual entry), 7 (joint handling: pain areas), 10 (Log screen) and 11 (security, cost). API facts are in `WHOOP_API_NOTES.md` (real field names confirmed).

**This plan is 2 of 5.** Plan 3 (rules, training engine, Plan tab) builds on these tables. It reads strength history for progression, pain for running holds, and VO2 max and weight for targets.

## Global Constraints

- **Public repo.** Never commit:
  - `docs/baseline.local.md`
  - `docs/baseline.local.json`
  - `*.local.*`
  - `.env*` (except `.env.example`)
  - `.data/`
  - any of the owner's health values

  Commit author: `288721429+jaredmcelreath-a11y@users.noreply.github.com`. Never push.
- **Auth.** Every server action and every non-public route calls `requireSession()` from `src/lib/auth/session.ts` itself.
- **No transactions** (neon-http). Writes are single idempotent statements (`on conflict`).
- **Local dates** are computed in `getEnv().OWNER_TZ` (default `America/Chicago`), never in UTC.
- **Canonical units in the DB:**
  - weight: pounds (`lb`)
  - distance: meters
  - duration: seconds
  - pool length: meters

  The UI accepts the owner's units and converts:
  - swim: yd (default) or m;
  - run: mi (default) or km;
  - bike: mi (default) or km.
- **Conversions** (exact constants):
  - 1 yd = 0.9144 m
  - 1 mi = 1609.344 m
  - 1 km = 1000 m
- **Pain areas:** default `["knee", "ankle", "shin"]`. Sides: `"left" | "right" | "both"`. Score: integer 0–10. Context: `"before_run" | "after_run" | "daily"`.
- **WHOOP matching:** a manual entry links to the WHOOP workout with the greatest time overlap within ±30 minutes, and only if `sport_name` fits the entry kind:

  | Entry kind | Matching `sport_name` |
  |---|---|
  | run | `running`, `activity` |
  | bike | `cycling`, `spin`, `activity` |
  | swim | `swimming`, `activity` |
  | strength | `weightlifting`, `weightlifting_msk`, `powerlifting`, `functional-fitness`, `activity` |

- **No new paid services. No AI features.**

## Review Focus

1. **Double-tap at the gym.** A flaky phone connection submits "complete set" twice. Expected: one set row. Each set carries a client-generated `client_id` (UUID) that is unique in the DB, and inserts use `on conflict do nothing`. Test: Task 4.
2. **Two weigh-ins on one day.** Expected: the latest replaces the earlier one. One row per local date (unique). Test: Task 3.
3. **Logging at 11:30 pm Chicago.** Expected: the entry belongs to that Chicago date, not the next UTC day. Test: Task 1 (`localDate`) and Task 3.
4. **Bad numbers.** Empty, negative, `"1,5"`, or absurd values such as 2,000 lb or 500 km. Expected: the server action rejects them with a readable message and writes nothing. zod bounds live in one module. Test: Task 2.
5. **Deleting history.** Deleting a session removes its sets. An exercise with past sets can't be deleted; it can only be archived, so "last time" and Plan 3's progression keep working. Test: Task 4.

**Interfaces (Produces):**
- `findWhoopMatch(db, kind: "run" | "bike" | "swim" | "strength", start: Date, end: Date): Promise<string | null>`. Applies the Global Constraints rule (sport fit, ±30 min window, greatest overlap).
